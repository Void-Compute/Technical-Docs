# Backend H — Public Technical Overview

> **Publication status:** Public-safe architecture overview
>
> This document intentionally describes Backend H at the architectural and
> behavioral level. Implementation-specific details, reverse-engineering
> artifacts, proprietary material, exact compatibility mappings, captured data,
> internal identifiers, and reproduction procedures are not included.

---

## 0. What Backend H is

Backend H is Ghost's software-based OptiX compatibility backend for AMD GPUs.

Its purpose is to provide the execution semantics required by supported
OptiX-based workloads while using Ghost's existing CUDA/HIP compatibility
infrastructure underneath.

At a high level:

```text
Application / Renderer
        │
        ▼
     OptiX API
        │
        ▼
   Ghost OptiX Layer
        │
        ├── API / ABI compatibility
        ├── Module management
        ├── Program management
        ├── Acceleration structures
        ├── Shader binding
        ├── Launch management
        └── Device-side ray semantics
        │
        ▼
 Ghost CUDA/HIP Compatibility Layer
        │
        ▼
       HIP
        │
        ▼
     AMD GPU
```

Backend H is intended to provide functional execution rather than merely
returning successful API calls.

The backend is designed around semantic compatibility: applications should
observe the behavior expected from the supported subset of the OptiX
programming model without requiring an NVIDIA GPU.

---

## 1. Design goals

Backend H was designed around several constraints:

- operate on AMD hardware;
- integrate with Ghost's existing CUDA compatibility layer;
- avoid requiring NVIDIA-specific GPU hardware;
- consume dynamically generated shader programs;
- preserve the relevant execution semantics expected by the renderer;
- keep scene data resident on the GPU during execution;
- provide a software implementation of the required ray-tracing behavior;
- remain sufficiently modular that another backend can later provide
  hardware-accelerated ray tracing.

Backend H is therefore deliberately different from a conventional hardware
ray-tracing implementation.

It prioritizes compatibility and semantic correctness over exploiting every
hardware-specific feature available on a particular GPU.

---

## 2. Architectural components

The implementation can be viewed as several cooperating layers.

### 2.1 API compatibility layer

The API layer exposes the functions expected by the application and translates
them into Ghost's internal representation.

Its responsibilities include:

- context and object management;
- module management;
- program-group management;
- pipeline management;
- acceleration-structure management;
- launch configuration;
- shader-binding information;
- error and status propagation.

The application therefore interacts with a familiar API surface while the
actual execution is handled by Ghost.

---

### 2.2 Module translation

Backend H receives GPU program modules generated by the renderer.

Rather than assuming that a particular precompiled binary is available, the
backend processes the program representation at runtime.

The translation stage adapts the program's ray-tracing operations to the
execution interface supplied by Ghost.

The exact translation rules and internal symbol mappings are intentionally
not documented here.

They are implementation details of Ghost rather than part of the public
architecture.

---

### 2.3 Program and pipeline management

Applications normally construct ray-tracing programs from several logical
program types.

Ghost maintains its own internal representation of these objects.

The pipeline layer associates:

- program groups;
- entry points;
- shader-binding information;
- acceleration structures;
- launch configuration.

Backend H subsequently combines these components into an executable GPU
representation.

The precise linking and dispatch-generation mechanism is implementation
specific and intentionally omitted from this document.

---

## 3. Acceleration structures

Backend H maintains a Ghost-owned representation of the acceleration
structures required by supported workloads.

The implementation supports the conceptual hierarchy used by modern
ray-tracing APIs:

```text
Top-level structure
        │
        ├── instance
        │      └── bottom-level structure
        │              └── geometry
        │
        └── instance
               └── bottom-level structure
```

The backend is responsible for translating application geometry and instance
information into its internal representation.

Important properties include:

- GPU-resident geometry;
- instance transforms;
- instance visibility;
- shader-binding offsets;
- primitive identification;
- hit information;
- traversal state.

The internal memory layout is deliberately not part of the public interface.

---

## 4. Shader binding

Ray-tracing applications associate shader programs and application data with
records in a shader-binding structure.

Backend H maintains the necessary metadata to resolve these records during
execution.

Conceptually:

```text
Ray
 │
 ▼
Traversal
 │
 ▼
Hit / miss determination
 │
 ▼
Shader-binding lookup
 │
 ▼
Associated program
 │
 ▼
Application shader
```

The exact record format, dispatch representation, generated code, offsets,
and internal lookup mechanism are implementation details and are intentionally
not published.

---

## 5. Device-side execution

The central component of Backend H is its device-side execution runtime.

This runtime supplies the operations required by supported ray-tracing
programs, including concepts such as:

- ray state;
- launch coordinates;
- launch dimensions;
- payload state;
- hit attributes;
- primitive information;
- instance information;
- transforms;
- shader-binding lookup;
- intersection reporting;
- intersection rejection;
- ray termination;
- exception state.

The implementation maintains this state on the GPU.

This allows the renderer's ray-generation and shading work to remain part of
the GPU execution path rather than being converted into a host-side rendering
pipeline.

---

## 6. Software traversal

Backend H contains a software traversal implementation.

At a conceptual level:

```text
Ray
 │
 ▼
Candidate geometry
 │
 ▼
Intersection testing
 │
 ▼
Visibility / masking
 │
 ▼
Hit processing
 │
 ▼
Shader dispatch
```

The traversal implementation is responsible for preserving the relevant
observable semantics of the supported ray-tracing workload.

It handles the relationship between:

- rays;
- geometry;
- instances;
- transforms;
- primitive identifiers;
- hit attributes;
- any-hit behavior;
- intersection behavior;
- termination behavior.

The exact traversal algorithm, data structures, implementation constants,
generated device code, and optimization strategy are not disclosed in the
public documentation.

---

## 7. Execution model

A Backend H launch conceptually follows this process:

```text
Application launch
        │
        ▼
Validate launch state
        │
        ▼
Resolve pipeline
        │
        ▼
Resolve shader-binding information
        │
        ▼
Prepare GPU execution state
        │
        ▼
Dispatch GPU workload
        │
        ▼
Device-side traversal
        │
        ▼
Shader execution
        │
        ▼
Frame / result
```

The implementation uses Ghost's existing GPU memory and execution
infrastructure.

Only a small amount of launch configuration needs to cross the host/device
boundary for each execution.

The exact launch structures and synchronization implementation are internal
details.

---

## 8. GPU memory model

Backend H is designed around GPU-resident execution.

The general principle is:

```text
Application data
      │
      ▼
 Ghost-managed GPU resources
      │
      ▼
   HIP / AMD GPU
      │
      ▼
Device-side execution
```

Large render payloads and scene data are not intentionally converted into a
host-side rendering representation.

Ghost manages the lifetime and ownership of the resources required by the
backend.

The exact allocation, synchronization, caching, and resource-lifetime
mechanisms are implementation details.

---

## 9. Compatibility philosophy

Backend H does not attempt to reproduce every feature of the complete
ray-tracing API.

Instead, Ghost implements the subset required by its supported workloads and
expands coverage as new workloads expose additional requirements.

This is important because compatibility is treated as an empirical process:

```text
Workload
   │
   ▼
Observed requirement
   │
   ▼
Ghost implementation
   │
   ▼
Regression test
   │
   ▼
Expanded compatibility
```

Unsupported functionality is therefore handled explicitly rather than being
silently represented as a fully implemented feature.

---

## 10. Backend H and Backend V

Ghost contains multiple approaches to GPU ray tracing.

Backend H provides a software-execution path.

Backend V is intended to provide a hardware-accelerated Vulkan-based path where
the target GPU and workload permit it.

The two approaches share the higher-level Ghost compatibility layer but differ
in their execution mechanisms.

Conceptually:

```text
                 Ghost OptiX Layer
                        │
              ┌─────────┴─────────┐
              │                   │
              ▼                   ▼
         Backend H            Backend V
       Software RT          Hardware RT
              │                   │
              ▼                   ▼
             HIP               Vulkan
              │                   │
              └─────────┬─────────┘
                        ▼
                    AMD GPU
```

Backend H therefore also serves as an important compatibility baseline while
the hardware-accelerated path is developed independently.

## 11. Development methodology

Backend H was developed incrementally.

The implementation was brought through several stages:

1. API loading and compatibility.
2. Object and state management.
3. Program representation.
4. GPU execution infrastructure.
5. Acceleration-structure handling.
6. Shader-binding support.
7. Device-side execution.
8. Software traversal.
9. Renderer integration.
10. Regression testing.

Each stage was validated before being incorporated into the next stage.

This approach is important because failures in a compatibility layer can
otherwise appear far away from their actual cause.

---

## 12. Testing philosophy

Testing focuses on behavior rather than simply checking whether an API call
returns success.

Relevant validation categories include:

- API lifecycle;
- invalid input handling;
- module processing;
- pipeline construction;
- acceleration-structure handling;
- shader-binding behavior;
- launch configuration;
- device execution;
- traversal behavior;
- resource lifetime;
- synchronization;
- renderer integration;
- regression behavior.

Ghost also maintains lower-level compatibility tests independently of the
renderer.

This allows implementation changes to be checked without requiring a full
application run for every regression.

---

## 13. Current scope

Backend H is intended as a compatibility implementation for supported Ghost
workloads.

It is not claimed to be a complete implementation of every feature exposed by
the upstream ray-tracing API.

Features outside the supported workload are intentionally treated as separate
engineering work.

This includes advanced geometry and ray-tracing features that are not required
by the current compatibility target.

---

## 14. Relationship to Ghost

Backend H should not be considered a standalone product.

It depends on the surrounding Ghost infrastructure for:

- GPU compatibility;
- CUDA compatibility;
- memory management;
- runtime integration;
- renderer integration;
- diagnostics;
- testing.

Its purpose is to extend that infrastructure into workloads that normally
expect a different GPU execution environment.

## 17. Summary

Backend H is Ghost's software ray-tracing compatibility backend for AMD GPUs.

It translates the requirements of supported OptiX workloads into an execution
model that can operate through Ghost's CUDA/HIP compatibility infrastructure
on AMD hardware.

The architecture consists broadly of:

```text
OptiX-compatible application
          │
          ▼
     Ghost OptiX API
          │
          ▼
   Program / pipeline layer
          │
          ▼
 Acceleration + SBT state
          │
          ▼
 Device execution runtime
          │
          ▼
 Software traversal
          │
          ▼
      HIP / AMD GPU
```

The implementation deliberately keeps the detailed translation machinery,
reverse-engineering evidence, private layouts, internal mappings, and
reproduction material outside this public document.

This document therefore serves as an architectural description rather than an
implementation manual.
